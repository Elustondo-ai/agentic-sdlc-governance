# Evidence-based continuation

Use this contract when a skill or specialist offers a next step. It grants no new execution authority.
The onboarding pilot connects Init, Status/Suggestion and Purpose; other specialist openings remain unchanged until reviewed.

## Choose the perspective

| Invocation | Recommendation scope |
| --- | --- |
| Direct Suggestion with a selected specialist | That specialist's useful next contribution, informed by the project |
| Direct Suggestion with no specialist or Governance selected | Project-wide priority |
| Status, including its call to Suggestion | Project-wide priority; report conversation focus separately |
| Explicit user request for another assessment scope | Honor that scope within existing authority; preserve focus |

Identify the perspective briefly: “Purpose recommendation” or “Project-wide next step”.
An introductory “From the Purpose perspective…” also works; do not repeat a role prefix on every reply.
Project-wide assessment neither activates Governance nor clears the selected specialist.
Unknown/lost role is not the Governance default: report the uncertainty, block dependent work and label any available advice as conditional.
The underlying facts and acceptance status must not change with perspective.

## Ground the next contribution

Resolve the target, current task, selected role, human decisions and applicable authority.
Keep methodology maintenance distinct from the consuming application's product priorities.
Reuse current evidence; inspect only what is needed to resolve the consequential gap or opportunity.
Distinguish scaffolds, substantive unregistered work, missing, stale, uninspected and contradictory evidence.
Use Intended / Actual / Planned; accepted documentation and passed tests do not establish delivered user value.
Prefer one concrete action, focused domain question or advisory handoff, with its reason and expected result.
Continue already assigned in-scope work; do not ask permission again for routine steps within that assignment.
Suggestion itself returns advice only. Status also returns a report, without executing its recommendation.
If work belongs elsewhere, name an existing selector only after checking its catalogue/adapter and boundaries.
A recommendation is not selection, delegation, observed delivery, approval or a lifecycle transition.
Do not manufacture work within a specialty when its useful contribution is complete.

## Keep the conversation useful

Respect the user's deferrals and rejected advice; repeat it only when new evidence changes its basis.
Retain these choices in this conversation, not a new shared role file or recommendation database.
Ask a question only when the answer advances the task or materially changes the recommendation.
Avoid generic endings such as “What would you like to do next?” and redundant requests to begin an interview.
Facts-only requests, acknowledgments, explicit stops and terminal closure need proportionate responses without added advice.
Only recommend installed skills; Handoff, Close and consistency checks are not installed by this pilot.
Report denied tools or inaccessible evidence specifically; unread material is not empty and a denial is not permission to bypass.

## One assessment path

Status passes its fresh evidence and project-wide scope to Suggestion once, unless facts-only.
Suggestion never calls Status back; additional inspection is justified only by a concrete evidence gap or changed source.
Purpose opening reuses factual Status evidence and its local assessment; it does not add a second project-wide suggestion.
These are conversation rules, not a new persistent state schema or proof of native enforcement.
