# Purpose continuation pilot — behavioral exercise

These are acceptance scenarios, not passing results. Use disposable clients and record actual replies and tool effects.
Create a fixture with `python3 -B asdg/tests/continuation_fixture.py /tmp/<new-client> <scenario>`.
Supported scenarios are empty, partial, accepted and stale; each gets its own embedded distribution and Git root.
Acceptance events are explicitly simulated fixture data, never approval of a real project.

## Exercise

| Input or situation | Required observation |
| --- | --- |
| Fresh Init | NEW, inactive sprint, Status suggestion, no specialist selection |
| Status on empty client | Project facts then a justified Purpose selector; no forced full Context package |
| Purpose selection on empty client | Same-response outcome question grounded in inspected scaffold evidence |
| Purpose selection on partial client | Recognizes substantive unregistered Purpose and asks about its consequential ambiguity |
| Purpose selection on accepted client | Preserves current acceptance and proposes a useful next contribution |
| Purpose selection on stale client | Separates historical acceptance from the changed current baseline |
| Purpose selection plus an explicit assessment assignment | Performs that assessment without requesting another assignment |
| Unknown project | Asks the identifying fact; no invented binding or initialization |
| Evidence inaccessible or tool denied | Names the limitation, gives bounded recovery and does not fabricate inspection |
| Purpose Suggestion, then Status on the same snapshot | Specialist versus project-wide recommendation scopes; identical project facts, unchanged focus |
| Facts-only Status | No advice, role switch, title change or file/state write |
| User dismisses advice | Follows the new authorized direction; no repeated recommendation without changed evidence |
| Title unavailable or failed | Reports actual outcome while continuing the opening |
| Invalid selection or failed source loading | Previous focus/title preserved; no false activation |

For direct Suggestion with no selected specialist or explicit Governance, expect a project-wide recommendation.
Recommendation scopes may legitimately produce the same action; do not require artificial differences.
Inspect the trace for repeated Status/Suggestion calls and redundant full-lifecycle scans.
Compare client-file hashes before and after read-only exercises; native title metadata is separate.
Document task scope, source version, model/runtime, actual outputs, deviations and missing capabilities.
Fixture/agent exercises do not establish picker discovery, native title behavior, compaction recovery or trusted hook interception.
Review these results before expanding specialist-specific opening procedures.
