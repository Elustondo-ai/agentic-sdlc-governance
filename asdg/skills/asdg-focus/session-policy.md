# ASDG conversation focus policy — pilot 0.2

This is a repository instruction for conversation behavior, not a native Codex mode or security boundary.
Its activation and status capabilities are [Focus](SKILL.md) and [Status](../asdg-status/SKILL.md).
Explicit native delegated assignments remain valid; these skills do not spawn or replace them.

## Selection

A genuinely new conversation starts with no selected specialist; general repository guidance still applies.
Explicitly selecting a named Focus skill, or a valid generic selector, requests one existing catalogue role, stages 01-12.
Select the role only after the canonical definition and required sources were successfully read.
Inspecting, maintaining, mentioning or reading a role package by itself NEVER activates that role.
Status, another ordinary skill, a topic change or a directory change NEVER selects or clears focus.
An explicit focus-clear request clears the selection; it grants no new permissions.
Invalid input or a failed activation leaves the previous selection unchanged and records the failure.
If its required guidance is unavailable, retain the declaration but block specialist work until resolved.

## Later turns

Apply the selected role to subsequent tasks without requiring the activation skill to be re-invoked.
This retains the user's responsibility assignment, not a promise that skill contents are injected every turn.
When asked who you are, name the selected role and actual boundaries; do not claim a spawned subagent.
Keep one selection and its activation receipt in THIS conversation, never in a shared ACTIVE_ROLE file.
Do not inspect other conversations or user-wide session logs to reconstruct the selection.
A role's lifecycle stage does not establish the target project's current lifecycle stage.
Retain target project, latest task and actual source-read evidence without inventing any of them.
Unknown target project does not block an introductory role interview.
For project-specific work, require the evidence and bindings demanded by the canonical contract.

## Recovery and boundaries

On resume or compaction, use only a retained, unambiguous activation receipt or explicit user reaffirmation.
If selection history was lost, report UNKNOWN: REACTIVATION_REQUIRED; do not silently assume None or Purpose.
Reread the canonical sources when retained context is insufficient or source changes matter.
Status reports what is known and may inspect necessary sources, but must not silently reactivate a role.
Keep earlier reads distinct from reads performed for this status report.
Apply the canonical out-of-scope and blocked-action rules; textual handoffs are not completed delivery.
All current catalogue roles allow conversation proposals, not project-file mutations or lifecycle execution.
Changing Codex Plan/Default mode or invoking a skill does not widen that authority.
Never infer runtime permissions, human approval, effective hooks or successful tests from role instructions.

## Current-chat title

Successful Focus activation/clear also requests [native current-chat renaming](rename-chat.md).
This narrow metadata exception permits no file rename, deletion, internal-store edits or changes to another chat.
A title displays focus; editing it never selects a role. Status never renames. Rename failure preserves focus.

## Acceptance

Run [the fresh-conversation exercise](TRY-IT.md); record observed successes and failures separately.
Native discovery, multi-turn retention, resume and compaction require actual Codex runtime tests.
