# Annex R01 — Design Docs Are All You Need

This is a research reference that I think deserves its own slide. The paper is “Design Docs Are All You Need,” by Samuel Kushnir and colleagues, published as an arXiv preprint in September 2026. It describes SMART, a symbolic tool for modeling machine-learning system performance. I first encountered it through a commentary post, but the workflow on this slide comes from the paper itself. The paper is available at https://arxiv.org/abs/2609.05364.

SMART's main branch contains almost no implementation code. It holds about fifty natural-language design documents, organized by dependencies. Read-only agents infer the dependency graph, and an orchestrator assigns bounded coding tasks in the right order. The generated library is checked against tests and hand-audited reference models before replacing the previous build. When agents struggle with a document, the orchestrator records the ambiguity so humans can improve that document. The authors report that a full rebuild takes around one and a half to three hours at about one hundred US dollars in their setup.

The paper is especially interesting because the documents include worked examples with specific intermediate values and expected outputs. This makes a rule less open to interpretation and gives the generated tests something concrete to reconcile. I would bring that into SDLC 2: dependency links among artifacts, small worked scenarios, expected results, and a visible record of where agents had to guess. These can help a human review both the proposed design and the implementation.

There is also a boundary to respect. SMART studies a specialized symbolic library with a small, stable intermediate representation. Matching hand-audited reference models to round-off precision is strong evidence of faithful regeneration for those modeled cases. It does not show that every production application can discard its code or that a performance model predicts real-world behavior perfectly. SDLC 2 has a broader scope: it governs intent through operation and learning at product, release, and sprint levels. Full regeneration is one possible implementation technique under that governance, not a rule of the method.
