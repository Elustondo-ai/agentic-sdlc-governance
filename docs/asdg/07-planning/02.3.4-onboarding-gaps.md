# ZIP or Clone, Script or Prompt: one installation engine

ASDG should arrive through either a ZIP or a pinned clone, then initialize through a script or a conversational prompt using identical deterministic code.
The existing Python initializer is the implementation to extend; a prompt should select explicit inputs and invoke it, never synthesize an alternative set of configuration files.

![The shared package selection and initialization path already implements the ZIP-to-project core.](../../../asdg/docs/images/distribution-flow.svg)

| Entry route | Actual support | Remaining work |
| --- | --- | --- |
| ZIP + Script | Builder selects one portable folder; extracted clients initialize through init.py/CLI. Disposable extraction, relocation and repeat tests pass. | Add an integrated artifact/manifest preflight and a reviewed installation plan; retain current collision refusal. |
| ZIP + Prompt | CODEX-PROMPT.md and the client-aware Init skill call the same local initializer after extraction. | Generalize the copyable prompt for either client and explicit source/client choices; test that it delegates all managed writes and honors denial. Native invocation remains unverified. |
| Clone + Script | The provider can build a ZIP; its full cloned asdg/ also contains excluded provider tools. `initialize` requires embedded source and target roots to match. | Stage only package-files.json members from a pinned local clone into a client; validate identity/version/hashes and exclude source .git, provider-only files, application evidence and state. Do not copy the whole clone. |
| Clone + Prompt | No portable clone-install handoff exists; the current prompt requires asdg/ already present. | Use the same clone-to-package staging and installation plan as Script; the prompt supplies source, target, ref and client, then invokes Python. |

“Clone” here means acquiring a canonical distribution from a clone into a separate adopting project. Developing ASDG inside its provider clone is a different activity and must not initialize that provider as an application.
Network cloning/fetching, dependency installation and Git initialization are not necessary inside the first engine increment: accept an existing clone pinned to a verified commit. Any future acquisition wrapper needs its own explicit authorization.
Current promote/upgrade requires Git roots, origins and HEADs, so an extracted ZIP is not a supported synchronization source yet. Normalized source identity must use an archive digest/manifest or a verified clone commit honestly; never fabricate Git provenance. First initialization must still accept an existing fresh Git root without requiring a remote or first commit.

## Small implementation increments still needed

1. Add source normalization around `distribution_files.package_files`: verified ZIP extraction or a pinned clone produces the same selected bytes and provenance. Reject escaping members, symlinks, duplicate paths and unexpected source/target identities.
2. Extract a planning step from `cli_project.initialize` so it can read the normalized source while planning into an explicitly identified existing Git root. Preserve current bootstrap, client renderers, state validation and `cli_files.apply`; remove no guard or migration check.
3. Preflight distribution placement and integration together before writes. Bind the plan to source bytes, target before-hashes, client choice and normalized initialization inputs, including the creation timestamp; refuse changed inputs at apply. Avoid copying asdg/ first and discovering an adapter conflict afterward.
4. Read adopted version/catalogue identity from the selected verified package rather than assuming an unrelated launcher's global VERSION. Record acquisition provenance plus generated-file baselines for the [separate integration refresh](02.3.3-integration-refresh.md).
5. Keep Script and Prompt as thin callers of this engine. The prompt may ask optional orientation questions; orientation is separate client documentation, never accepted Purpose or a hidden initialization algorithm.
6. Test all four routes against the same normalized package and inputs: equal methodology hashes and generated configuration, equivalent state with fixed volatile inputs, repeat idempotency, collisions, partial-write rollback and preservation of application files. Observe native Prompt invocation separately.

This requires small acquisition/planning adapters and baseline metadata, not another agent, database, daemon, package manager or lifecycle state engine.
Do not claim a validated distribution from a matching manifest alone: bind test evidence and a separate exact-state human release decision to its snapshot when preparing distribution acceptance.
The current 117-test result covers the existing engine and synchronization fixes; it does not demonstrate Clone ingestion, a refresh command or the four-route equivalence tests proposed here.
